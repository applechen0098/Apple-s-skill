# LFF / 3PF 会话问题与客服方案标注规则（两阶段版）

## 1. 分析目的

先对每条会话忠实提取“卖家具体问题—适用条件—客服实际方案”，再让全部有效会话进入卖家问题聚类。`人工介入类型`和`知识可复用性`不是聚类前的筛选条件，只用于问题聚类完成后的能力分流。只有完成聚类后，才按问题簇评估现有 SKB solution、API / Taskflow 或人工承接能力，并生成 Optimization plan。

本流程的首要目标是高效、准确地识别高频卖家问题和可复用客服方案。RC 下的 SKB 覆盖程度属于可选分析，不再作为逐会话标注的必填内容。

### 任务输入和写入位置必须由用户提供

本规则不绑定任何历史对话记录文件、Google Sheet URL、spreadsheet ID、tab 名、行范围或标注输出位置。每次开始标注、复核或续标前，必须从用户当前请求中获得或再次确认：

- 读取哪一个对话记录文件/Spreadsheet；
- 读取哪一个 tab/sheet 和哪些 1-based 物理行；
- 哪些表头字段分别对应 `live_agent_chat_session_id`、`msg_data`和 L3 reason；
- 标注写回哪一个文件/Spreadsheet、tab/sheet 和哪些目标字段/列；
- 写回位置是否就是对话记录来源表，还是另一张目标表。

缺少或存在歧义时，必须先询问用户，不得复用上一次任务、示例或工作区中的路径、链接、Sheet 名和列号。

## 2. 两阶段流程

### 阶段一：逐会话最小标注

- 阅读每条完整真实会话。
- 提取卖家的具体问题、影响答案的适用条件和客服实际提供的方案。
- 判断本次客服是否进行了后台数据查询或处理执行。
- 判断客服回复是否可以形成通用知识答案。
- 不检索 SKB，不判断完全覆盖、部分覆盖或未覆盖，也不在单条会话中编写 SOP 优化建议。

### 阶段二：问题聚类与知识分析

- 汇总全部有效会话标注结果；空白会话和重复 session 不进入统计。
- 先按卖家具体问题和会改变答案的适用条件形成卖家问题簇，不得因人工介入类型或知识可复用性不同而提前排除会话。
- 在同一卖家问题簇内，再按客服方案、数据查询、处理执行和回复完整度整理解决方式变体；客服方案冲突时不得静默合并。
- 统计问题簇频次并识别高频问题。
- 在问题簇层级分别判断需要的能力：QA、API / Taskflow（SOP）或人工承接 / 流程自动化；知识负责人待确认事项作为依赖记录，不单列行动类型。
- 对需要采取行动的问题簇生成对应类型的 Optimization plan；一个问题簇可以产生多条不同能力路线的 action。
- 如需统计 SKB 覆盖程度，将问题簇的覆盖结论映射回簇内会话；不得把未评估视为未覆盖。

Optimization plan 的`行动类型`只使用以下3类：

- `QA`：问题可以通过稳定、直接的规则、流程解释、步骤或链接回答，不需要读取具体卖家的订单、店铺、商品、物流、库存、配置或案件信息，也不需要复杂条件判断。优先补充现有 `solution_type_name = QA` 的 solution；没有合适 QA 时新增 QA solution。
- `API/Taskflow`：答案必须根据卖家的具体信息、对象级后台状态、变量、订单/店铺选择器、复杂条件或高阶自助流程判断。此类行动必须落到 `solution_type_name = SOP` 的 solution；优先补充现有 SOP，没有合适 SOP 时新增 SOP。
- `人工承接/流程自动化计划`：需要登记、建单、申诉、催促、升级、提交专员、补充材料或其他人工处理执行；同时识别可自动化的材料收集、建单、编号返回、状态通知等步骤。

`待确认`不再是行动类型。客服答复不完整、条件不足、口径冲突、业务归属不明、接口字段缺失、SOP/issue 映射缺失、样本不足或低频长尾等情况，必须写入`待Owner确认/依赖`或`备注`。能够判断最终能力路线时，仍归入 QA、API/Taskflow 或人工承接；无法安全判断行动路线时保留在未决/长尾池，不编造第四类行动。

同一问题簇包含不同解决方案时，不拆成互不相关的问题簇，也不把多种能力堆在同一行动行。应保留同一个基础 Cluster ID，并按能力或独立行动拆行，例如`C01-Q1`、`C01-A1`、`C01-H1`。问题簇共享字段在各行动行重复填写，行动证据只填写支持本行方案的来源会话。不同 QA solution 或不同 SOP solution 必须分别建立行动行；同一 solution 下条件相容的分支可以合并，但必须写清条件。相互冲突的方案保留在最匹配的行动行，并把冲突写入`待Owner确认/依赖`。若实际是多个可分别回答的卖家意图，则按多意图规则进入不同问题簇，而不是作为同一问题的多方案处理。

QA 与 SOP/API 必须分别维护 solution 和 issue 字段：QA 行填写 QA Solution ID、QA issue_id、QA issue_name 及条件式 issue-description 增量；API/Taskflow 行填写 SOP Solution ID、SOP issue_id、SOP issue_name 及条件式 issue-description 增量。一个行动行只允许一个 solution ID；同一行动需要修改两个 SOP 时必须拆成两行。

详细聚类、覆盖评估和 Optimization plan 规则见 [optimization-plan.md](optimization-plan.md)。

## 3. 必须遵守的真实对话边界

- 一条完整 `live_agent_chat_session_id` 为一个分析单元；用户指定的 `msg_data` 表头字段是卖家进线及其与人工客服完整对话的主要标注来源，不得假定其位于固定列。
- 必须阅读该行完整 `msg_data`；重复 session 不重复标注，空白会话跳过。
- 卖家问题、适用条件、客服方案和可复用内容只能来自本条真实对话，不得使用其他会话、现有 SOP、经验、常识或推断补足。
- 不得把卖家自己提出的操作、猜测、要求或排查尝试写成客服提供的解决方案。
- 客服未说明、对话未提供或回复未完成时，必须如实写明，不得自行补全。
- 保留 L3 reason、原表行号和 `live_agent_chat_session_id`，用于后续分层分析、证据回查和回归测试。

## Row Identity Lock（强制执行）

### 1. 物理行号是不可变主键

Google Sheet 的 1-based 物理行号是每条标注记录的不可变主键。不得使用过滤后的数组序号、有效会话序号、批次内序号、循环索引或已处理记录数量推导写入行号。

### 2. 为每个来源行建立 manifest

用户指定范围内的每一个物理行都必须在批次 manifest 中保留一条记录，并至少保存：

- `source_sheet_id`；
- `source_row`：Google Sheet 1-based 物理行号；
- `live_agent_chat_session_id`；
- `msg_data_present`；
- `annotation_fields`；
- `row_status`：`ANNOTATE`、`SKIP_EMPTY`或`SKIP_DUPLICATE`。

`source_sheet_id`必须使用连接器/API返回并实际用于读写的来源 Sheet 标识，不得自行猜测或转换。`annotation_fields`必须按字段名保存，不得依赖列字母或数组位置。

### 3. 空行和跳过行不得压缩

读取时不得压缩、删除或重新排序空 `msg_data` 行。空行必须以`SKIP_EMPTY`占位保留在批次映射中，其目标标注列必须保持为空。按既定去重规则跳过的重复 session 使用`SKIP_DUPLICATE`占位，同样不得导致后续物理行前移。

### 4. 写入前重新锁定行身份

写入任一标注行前，必须重新读取该 `source_row`，并验证：

```text
source_row 当前的 live_agent_chat_session_id
= manifest 保存的 live_agent_chat_session_id
```

不一致时禁止写入并停止当前批次。对于`SKIP_EMPTY`行，还必须验证 `msg_data` 仍为空；对于待标注行，必须验证 `msg_data` 仍存在。

### 5. updateCells 只能由 source_row 定位

使用 Google Sheets `updateCells` 时，目标行必须直接由物理行号计算：

```text
startRowIndex = source_row - 1
```

不得由循环索引、过滤后数组位置、有效记录数量或批次内序号计算。目标列只能是用户指定的标注列。

### 6. 每批最多10个物理行并强制回读

每批最多处理10个连续物理行，而不是10条过滤后的有效记录。写入后必须回读同一批次的：

- `source_row`；
- `live_agent_chat_session_id`；
- `msg_data`；
- 全部目标标注列。

逐行与写入前 manifest 核对。空行和重复 session 的 SKIP 占位也属于批次校验范围。

### 7. success 不是完成标准

Connector/API 返回`success`只代表请求被接收，不代表写入正确。只有回读同时满足以下条件，当前批次才算成功：

```text
expected source rows = actual annotated rows
missing rows = []
unexpected rows = []
session_id mismatches = []
blank-msg_data rows with annotations = []
duplicate written rows = []
```

其中`expected source rows`只包含 manifest 中`row_status = ANNOTATE`的物理行；`SKIP_EMPTY`和`SKIP_DUPLICATE`必须保持目标标注列为空。

### 8. 校验失败立即停止

一旦任何一行校验失败：

- 不得继续下一批；
- 重新读取当前批次的原始 `msg_data`、session ID 和目标标注列；
- 只修正当前批次，不扩大写入范围；
- 再次通过完整校验后才能继续。

### 9. 多意图仍锁定在原物理行

多意图会话仍只写在原来的一个物理行中：

- 每个独立意图分别编号或换行提取；
- 不得新增 Sheet 行；
- 不得把后一个意图写到下一物理行；
- 聚类阶段可以让同一个 `source_row` / `live_agent_chat_session_id` 进入多个问题簇。

### 10. 禁止结构性改动

标注期间禁止排序、在过滤结果上按可见顺序写入、插入行、删除行或移动行。只能更新用户指定的标注列，不得覆盖来源字段、公式或其他无关列。

### 11. 生成 Optimization plan 前的最终集合校验

完成用户指定的全表或完整范围标注后，必须验证：

- 有效源行集合 = 已标注行集合；
- 每个已标注行的 session ID 与源行一致；
- 所有空 `msg_data` 行的标注列保持空白；
- 所有按规则跳过的重复 session 行保持空白且不引起行号偏移；
- 所有多意图会话的意图均保留在原物理行；
- `missing rows`、`unexpected rows`、`session_id mismatches`、`blank-msg_data rows with annotations`和`duplicate written rows`均为空集合。

这里的“有效源行”指 manifest 中`row_status = ANNOTATE`的物理行。最终集合校验未通过前，不得生成 Optimization plan。

## 4. 每条会话只回答以下 6 个问题

以字段名称为准，不依赖历史列字母。

| 问题 | 建议字段 | 填写要求 |
| --- | --- | --- |
| 1. 卖家的具体问题是什么？ | 卖家具体问题 | 单意图时使用卖家能够直接向 Chatbot 提问的粒度，一句话概括最终核心诉求；多意图时在同一单元格内按`意图1：……`、`意图2：……`编号列出，不拆来源行。 |
| 2. 哪些条件会影响答案？ | 适用条件 | 只保留会改变方案的站点、订单或履约类型、订单状态、物流渠道、仓库、ERP、库存或店铺配置等条件；多意图时按`针对意图1：……`对应填写；对话未说明则写明未说明。 |
| 3. 客服实际提供了什么方案？ | 客服提供的解决方案 | 只写客服明确提供的事实、规则、建议、操作路径、链接、查询结果和已执行动作；多意图时按`针对意图1：……`对应填写，未回答的意图明确写`意图n未完成答复`。 |
| 4. 是否需要人工介入？ | 人工介入类型 | 按整个会话实际发生的最高动作，只使用：`否：仅解释或指引`、`是：数据查询`、`是：处理执行`。 |
| 5. 人工具体做了什么？ | 查询/执行信息及结果 | 仅当存在数据查询或处理执行时填写；写清输入、动作和结果，并注明对应的意图编号。 |
| 6. 客服回复是否可形成通用知识？ | 知识可复用性 | 按整个会话和本节规定的优先顺序，只使用：`可形成通用答案`、`仅个案查询结果`、`仅人工处理`、`客服回复不完整`。 |

不再逐会话填写以下内容：

- SKB 覆盖结论；
- SKB 覆盖判断依据；
- solution 优化建议；
- 可直接复用的 Chatbot 答案。

这些内容在问题聚类后按问题簇统一产生。

### 标注证据与 Chatbot 答案的角色边界

- `客服提供的解决方案`和`查询/执行信息及结果`是内部证据字段，可以使用`客服说明……`、`客服查询……`、`客服提供……`等分析口吻。
- 上述证据字段不得原样复制为 Optimization plan O 列的`可直接复用的答案`。生成 O 列时必须提取其中由客服明确支持的条件和方案，改写为 Chatbot 直接面向卖家的第二人称答案。
- `客服未查询到`只证明本次客服没有找到或确认信息，不自动等于`平台没有该信息/价卡/能力`。除非对话中的客服明确作出后一结论，否则不得在 Chatbot 答案中强化为平台规则；应把缺失口径写入`待Owner确认/依赖`，无法安全判断能力路线时保留在未决池。
- 若客服只使用`通常`、`一般情况下`等模糊口径，且对话没有提供可替代的明确条件，不得删掉限定词并改写成确定规则；该内容应标记为条件不足并写入`待Owner确认/依赖`，不形成可直接复用答案。

## 5. 卖家具体问题和适用条件

### 卖家具体问题

不能只写宽泛主题，例如“3PF 发货问题”“海外仓物流问题”。应写成卖家可直接提问的问题，例如：

- `订单已选择 Pick-up 后能否改为 Drop-off？`
- `越南一店多运的同一全球商品链接能否同时从本地仓和跨境仓发货？`

一条会话存在多个独立问题时，应分别提取；逐会话标注阶段仍保留为一个来源行，后续聚类时再分别处理，并保留同一来源 session。

### 多意图会话

#### 何时拆成多个意图

满足以下任一条件时，应拆成多个独立意图：

- 各问题可以分别回答；
- 各问题具有不同的适用条件；
- 各问题分别需要 SOP、API / Taskflow、人工处理等不同能力。

如果只是对同一问题补充背景、追加信息、澄清条件或继续追问同一结果，则保留为一个意图，不得机械拆分。

#### 同一来源行的填写方式

逐会话标注时，不选择一个“主意图”而丢弃其他问题，也不把同一会话拆成多个来源行。应在原行对应单元格内编号，并让问题、条件和客服方案一一对应：

```text
卖家具体问题：
意图1：越南3PF服饰类目的佣金率是多少？
意图2：该订单为什么被收取CIT？

适用条件：
针对意图1：越南站点；3PF服饰类目。
针对意图2：越南站点；客服明确说明的订单时间和适用主体。

客服提供的解决方案：
针对意图1：客服提供费率文章及类目查询方式。
针对意图2：客服说明CIT适用主体、订单时间和税率。
```

某个意图未获得完整答复时，必须在对应位置明确写`意图2未完成答复`，不得用其他意图、其他会话、SOP 或推断补全。

#### 会话级标签

`人工介入类型`和`知识可复用性`均按整个会话只标记一个结果，但问题、适用条件、客服方案和查询/执行内容仍须按意图编号对应。

- 人工介入类型按最高实际动作判断：发生处理执行 → `是：处理执行`；无执行但发生对象级后台查询 → `是：数据查询`；只有解释、链接或仅确认履约类型 → `否：仅解释或指引`。
- 知识可复用性按以下顺序判断：任一独立意图未回答完整或缺少必要结论 → `客服回复不完整`；否则，全部意图回答完整且存在明确通用规则、步骤或链接 → `可形成通用答案`；否则，全部只是具体订单、店铺或商品查询结果 → `仅个案查询结果`；否则，全部只是登记、升级、催促等执行 → `仅人工处理`。

### 适用条件

只记录会改变答案或处理路径的条件，例如：

- 站点；
- 3PF、PFF、SLS、本土、跨境或官方仓等订单/履约类型；
- 待发货、已安排发货、已生成面单等订单状态；
- Pick-up、Drop-off 或具体物流渠道；
- ERP 推单、仓库绑定、库存或店铺配置；
- 客服明确提供的时间节点、门槛或前置动作。

禁止仅因条件和方案同时出现在对话中，就自行推断二者存在适用关系或因果关系。

## 6. 人工介入判断

人工介入类型是会话级标签。多意图会话按整个会话实际发生的最高动作标注，优先级为：`是：处理执行` > `是：数据查询` > `否：仅解释或指引`。`查询/执行信息及结果`必须注明动作对应哪个意图；不得因一个意图仅需解释而忽略另一个意图已经发生的数据查询或处理执行。

### 否：仅解释或指引

客服仅解释规则、提供 SEH/联系方式、建议卖家自行操作，或根据订单号确认 3PF、SLS、跨境、本土等订单类型后给出通用规则。

仅根据订单号确认订单属于 3PF、SLS、本土、跨境、Pick-up、Drop-off 等履约类型，并据此选择通用规则，不算后台数据查询型人工介入，也不生成“根据订单号查询履约类型”的 API / Taskflow 需求。

此时必须：

- 在`客服提供的解决方案`中说明客服依据订单号确认了哪一种订单或履约类型；
- 在`适用条件`中保留该订单或履约类型，因为它可能改变问题分簇和答案；
- 仅当客服进一步查询并返回运单生成、物流分配、订单状态、异常原因、仓库扫描、库存、店铺配置或案件进度等对象级后台信息时，才标记为`是：数据查询`，并将具体查询内容作为 API / Taskflow 候选需求。

### 是：数据查询

客服使用订单号、运单号、店铺 ID、商品 ID 等信息查询后台，并返回该订单、店铺或商品的具体状态、配置、原因或结果。

使用简短格式：`输入：……；查询：……；结果：……`。

### 是：处理执行

客服已实际登记、建单、反馈后台、催促物流、升级案件、提交专员、补充材料或申请索赔。若同时存在数据查询，仍标记为 `是：处理执行`。

使用简短格式：`输入/材料：……；执行：……；结果/编号：……`。

仅索取信息、表示正在查询或完成转接，不算人工介入；必须以客服实际返回或执行的结果为准。

## 7. 知识可复用性判断

`知识可复用性`只用于问题聚类后的能力分流，不用于决定一条有效会话是否进入卖家问题聚类。`仅个案查询结果`、`仅人工处理`和`客服回复不完整`同样必须贡献问题频次：前两类分别支持 API / Taskflow 或人工承接 / 流程自动化计划；回复不完整项应记录依赖，能够判断能力路线时仍归入三类行动之一，无法判断时保留在未决池。

知识可复用性是会话级标签。多意图会话必须按以下优先顺序判断：

1. 任一独立意图未回答完整或缺少必要结论 → `客服回复不完整`；
2. 所有意图回答完整，且至少一个意图存在明确通用规则、步骤或链接 → `可形成通用答案`；
3. 所有意图均只得到具体订单、店铺或商品的查询结果 → `仅个案查询结果`；
4. 所有意图均只得到登记、升级、催促等处理执行 → `仅人工处理`。

这一会话级标签不取代意图级证据。Optimization plan 阶段仍须分别使用每个意图对应的客服回复、查询或执行内容，不能把一个意图的方案套到另一个意图。

### 可形成通用答案

客服明确提供了可以复用于其他卖家的规则、操作路径、条件化方案或官方链接。

### 仅个案查询结果

客服只返回某个订单、店铺或商品的后台查询结果，没有说明该结果对应的通用规则或处理方案。

### 仅人工处理

客服完成了登记、建单、催促、升级、申请或其他人工执行，但没有提供可由 Chatbot 直接复用的知识答案。

### 客服回复不完整

客服没有回答完问题，或缺少形成可复用答案所需的必要条件、步骤或结论。

如果同一会话既有数据查询/处理执行，又有明确的通用规则，且所有独立意图均已完整回答，则会话级知识可复用性可标记为`可形成通用答案`；人工介入类型仍按最高实际动作标注，查询/执行内容与通用规则仍须分别对应到具体意图。

## 8. 条件化提炼与脱敏

- 可以从单条会话中提取“适用条件 → 对应方案”，但条件和方案必须由同一条 `msg_data` 明确支持。
- 不得把某个站点、订单类型、状态或店铺配置下的个案方案扩大到其他场景。
- 禁止使用“一般情况下”“通常”“原则上”“大多数情况下”“视情况而定”等笼统表述代替适用条件。
- 删除或模糊处理订单号、运单号、店铺 ID、商品 ID、买家姓名、账号、电话、邮箱、详细地址、聊天编号等个案信息。
- 保留具有判断价值的站点、订单类型、状态、渠道和配置条件。
- 若客服只返回个案结果，应写：`客服仅返回个案查询结果，未提供可通用复用的答案。`
- 若客服提供方案但未说明必要条件，应写：`客服未说明该方案的适用条件，需知识负责人确认。`

## 9. 最短执行流程

1. 按连续物理行读取最多10行，为每行建立含 `source_sheet_id`、`source_row`、session ID、`msg_data_present`、`row_status`和标注字段的 manifest；空行和重复 session 保留 SKIP 占位。
2. 对每个`ANNOTATE`物理行单独读取完整 `msg_data`。
3. 判断会话包含一个还是多个独立意图；多意图时在同一来源行编号列出，不拆行。
4. 按相同编号填写卖家具体问题、适用条件和客服提供的解决方案；未答复的意图明确写明。
5. 按整个会话的最高实际动作判断人工介入类型；仅在数据查询或处理执行时填写具体动作、结果及对应意图。
6. 按多意图优先顺序判断会话级知识可复用性。
7. 写入前逐行重新读取并核对 session ID；使用`startRowIndex = source_row - 1`定位，只更新用户指定标注列。
8. 写入后回读同一批次的来源行、session ID、`msg_data`和全部标注列，并按 Row Identity Lock 完整校验。
9. 当前批次通过后自动继续下一批，直至用户指定结束行；完整范围通过最终集合校验后才可生成 Optimization plan。

脚本只可辅助读取、写入和结构校验，不可代替完整会话的语义判断。

## 10. 批次校验

- 行号、`live_agent_chat_session_id` 和 L3 reason 对应正确。
- manifest 中每个连续物理行均存在，`source_row`未由过滤或循环序号推导。
- 每条会话均填写卖家具体问题、适用条件、客服方案、人工介入类型和知识可复用性。
- 多意图会话没有只保留主意图，也没有拆成多个来源行；问题、条件、客服方案和查询/执行内容均按相同意图编号对应。
- 仅同一问题的补充描述或追问未被误拆为多个意图。
- 任一意图未完成答复时，知识可复用性已标为`客服回复不完整`，且未自行补全。
- 多意图会话的人工介入类型已按整个会话最高实际动作标注。
- 仅在数据查询或处理执行时填写具体人工动作。
- 卖家问题和客服方案没有混写。
- 客服方案没有超出本条 `msg_data`，没有把卖家行为写成客服方案。
- 个案信息已脱敏；条件化内容保留必要适用条件，没有使用笼统措辞补足。
- 内部证据字段允许使用`客服说明/查询/提供`等分析口吻，但已标明这些内容不得直接复制为卖家可见的 Chatbot 答案。
- 不存在逐会话 SKB 覆盖判断或 SOP 优化建议。
- `SKIP_EMPTY`和`SKIP_DUPLICATE`行的目标标注列保持为空，没有导致后续行错位。
- 回读结果满足：无缺失行、无意外行、无 session ID 不一致、无空 `msg_data` 行被标注、无重复写入行。

每批写入后必须回读并逐行校验，不得以 Connector/API 的`success`响应代替回读验收。任一行失败时停止后续批次，只修正当前批并重新完成完整校验。

## 11. 连续执行

- 用户指定范围后，连续处理至结束行；每批最多10个连续物理行，批次只是内部写入和校验节点，不是暂停点。
- 用户明确授权并行时，可拆为互不重叠的连续区间；各区间仍按本规则逐条判断，主任务完成边界检查后再结束。
