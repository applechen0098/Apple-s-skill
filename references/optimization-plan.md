# LFF / 3PF Chatbot Optimization Plan 生成逻辑（全量问题聚类与多能力分流）

## 1. 文档目的

本方法用于把逐会话提取的“卖家问题—适用条件—客服方案”转化为可执行的 Chatbot 优化计划。行动范围分为 QA、API / Taskflow（SOP）和人工承接 / 流程自动化计划；知识负责人待确认事项作为依赖记录，不作为第四类行动。

核心流程为：

> 逐会话最小标注 → 全量卖家问题聚类 → 高频问题排序 → 解决方式分流 → SKB / API / 人工承接 Optimization plan

SKB 不再在逐会话阶段重复判断。所有有效会话必须先贡献卖家问题频次，`人工介入类型`和`知识可复用性`只用于问题聚类后的能力分流，不得作为聚类前的筛选条件。

## 2. 信息来源与边界

- 本规则不绑定任何历史对话记录、Chatbot solution、issue-and-solution 或 Optimization plan 的文件路径、Google Sheet URL、spreadsheet ID、tab 名或写入位置。
- 开始分析前，必须由用户提供或明确确认：对话记录来源文件/Spreadsheet、tab/sheet 和物理行范围；逐会话标注字段所在位置；需要覆盖判断时的 Chatbot solution 来源；需要 issue 映射时的 issue-and-solution 来源。
- 需要写入 Optimization plan 时，必须由用户提供目标文件/Spreadsheet和准确的目标 tab/sheet；如果需要新建 tab/sheet，必须取得明确授权并确认名称。缺失或存在歧义时先询问用户，不得沿用历史任务、示例或本地工作区路径。
- 卖家问题、适用条件、人工客服回复、查询结果和处理动作，以用户指定对话记录中的 `msg_data` 表头字段为准，不得假定其位于固定列。
- 现有 Chatbot 答案，以用户指定的当前 solution 表中的完整 `message_content` 为准；其中会保留 SEH 链接，`message_content_plaintext` 只能辅助阅读。若 solution 表包含 `solution_type_name`、`node_id`、`node_name`和`answer_branch_name`，必须按实际字段读取，不得依赖历史列字母。
- 对 SOP 类型 solution，覆盖判断的最小答案变体是`Solution ID + node_id + answer_branch_name`。同一个 `node_id` 下的不同 branch 可能由卖家 metrics 触发并返回不同答案，必须分别判断，不得把多个 branch 的内容合并后宣称覆盖。`node_name`仅用于理解节点的大致用途，不能代替该 branch 的完整`message_content`作为覆盖证据。
- 逐会话阶段不使用现有 SOP 或 SKB 补写客服未说明的方案。
- 问题簇的汇总答案只能组合来源会话中客服已经明确提供、且适用条件相容的内容；每项内容必须能追溯到来源 session。
- 不得合并相互矛盾的客服答案，也不得用经验或常识解决冲突。

## 3. 端到端流程

1. 按 [annotation-rules.md](annotation-rules.md) 完成用户指定对话记录范围的最小标注。
2. 让全部有效会话按卖家具体问题和会改变答案的适用条件形成一级问题簇。
3. 统计每个问题簇的会话量，识别高频和高价值问题。
4. 在每个问题簇内部，按客服方案、数据查询、处理执行和回复完整度整理二级解决方式变体。
5. 将解决方式变体分流为 QA、API / Taskflow（SOP）或人工承接 / 流程自动化计划；待确认事项写入依赖字段。
6. 仅对知识路线检索当前 SKB solution，并判断完全覆盖、部分覆盖、未覆盖或未评估。
7. 对需要采取行动的问题簇生成对应类型的 Optimization plan；一个问题簇可以产生多条不同能力路线的 action。
8. 如需要 SKB 覆盖程度，将知识解决方式变体的覆盖结论映射回对应来源会话并计算分布。
9. 实施选定的 QA 或 SOP 修改时，同步维护对应 issue description，并使用来源问题回归测试。

## 4. 会话结果如何分流

全部有效会话先进入卖家问题聚类，再根据人工介入类型、知识可复用性和客服实际动作进行能力分流：

| 会话标注结果 | 后续路线 |
| --- | --- |
| `否：仅解释或指引` + `可形成通用答案` | 进入 QA 路线，比较当前 QA solution 覆盖并形成 QA 优化 action。 |
| `是：数据查询` + 同时存在明确通用规则 | 通用规则进入 QA 路线；对象级后台查询进入 API / Taskflow（SOP）路线。 |
| `是：数据查询` + `仅个案查询结果` | 进入 API / Taskflow 路线，不把个案结果泛化为知识答案。 |
| `是：处理执行` | 进入人工承接 / 流程自动化计划；若同时存在明确通用规则，可另生成 QA action。 |
| `客服回复不完整` | 保留在问题簇频次中；能判断能力路线时归入 QA、API/Taskflow 或人工承接并记录依赖，无法判断时进入未决池；不自行补写答案。 |

由此可分别衡量：

- **知识自助适用程度**：RC 下有多少会话可以通过规则或操作指引回答；
- **数据/API 需求**：有多少会话需要查询具体订单、店铺或商品信息；
- **处理执行需求**：有多少会话需要人工或系统实际完成操作。

### 履约类型确认不属于 API 需求

客服仅根据订单号确认订单属于 3PF、SLS、本土、跨境、Pick-up、Drop-off 等履约类型，并据此提供通用规则时：

- 不标记为人工数据查询；
- 不生成“根据订单号查询履约类型”的 API / Taskflow 需求；
- 在问题簇`适用条件`中保留该履约类型；
- 在客服方案或 solution 中说明该规则适用于哪一种履约类型。

只有客服进一步返回运单生成、物流分配、订单状态、异常原因、仓库扫描、库存、店铺配置或案件进度等对象级后台信息时，才将这些具体查询内容纳入 API / Taskflow 路线。

## 5. 形成具体问题单元

每条有效会话形成的问题记录包含：

1. 卖家能够直接向 Chatbot 提问的具体问题；
2. 会改变答案的适用条件；
3. 客服在这些条件下明确给出的方案；
4. 原表行号和 `live_agent_chat_session_id`；
5. L3 reason；
6. 人工介入类型和知识可复用性。

不能使用“3PF 发货问题”等宽泛主题。应落到例如：`订单已选择 Pick-up 后能否改为 Drop-off？`

### 5.1 多意图会话从标注到聚类的拆分

逐会话标注阶段，同一会话只保留一个来源行，不选择一个“主意图”而丢弃其他问题，也不复制成多行。独立意图在卖家问题、适用条件、客服方案和查询/执行内容中使用同一组编号对应：

```text
意图1：越南3PF服饰类目的佣金率是多少？
意图2：该订单为什么被收取CIT？

针对意图1：客服提供费率文章及类目查询方式。
针对意图2：客服说明CIT适用主体、订单时间和税率。
```

如果某个意图没有获得完整答复，保留`意图n未完成答复`，不得推断或用其他意图的方案补全。

满足以下任一条件时，视为多个独立意图：问题可以分别回答、适用条件不同，或分别需要 QA、API / Taskflow（SOP）、人工承接等不同能力。仅为同一问题补充背景、条件、信息或继续追问同一结果时，保留为一个意图。

Optimization plan 阶段再将各独立意图拆入相应问题簇。例如，同一会话可同时进入`3PF佣金和收费标准`和`越南CIT税费`两个问题簇；两个问题簇均保留相同的原表行号和 `live_agent_chat_session_id`。

会话级`人工介入类型`按最高实际动作标注，`知识可复用性`按标注规则中的多意图优先顺序标注。生成 action 时仍按意图级证据分流：只使用该意图对应的规则、查询或执行内容，不得把一个意图的客服方案用于另一个意图。

## 6. 问题聚类规则

采用两级聚类。

### 一级：卖家问题簇

只有以下两项一致时，才能合并为同一卖家问题簇：

- 卖家具体问题相同；
- 影响答案的适用条件相同。

出现以下情况时必须拆簇：

- 站点不同会改变答案；
- 订单或履约类型、订单状态、物流渠道、仓库或店铺配置不同会改变答案；
- 一条客服回复说明了适用条件，另一条没有说明且无法确认是否同一场景。

人工介入类型、知识可复用性或客服解决方式不同，不作为排除会话或拆分一级问题簇的唯一理由。

### 二级：解决方式变体

在同一卖家问题簇内，再按以下维度整理解决方式变体：

- 客服提供的通用规则、步骤和链接；
- 对象级后台查询的输入、动作和返回结果；
- 登记、建单、催促、升级或提交专员等处理执行；
- 客服回复是否完整；
- 客服答案或时间节点是否一致。

客服方案相互冲突时不得静默合并，应保留为不同变体并标记知识负责人确认。同一问题簇可以同时生成 SKB、API / Taskflow 和人工承接 action。

每个问题簇必须保留：

- 问题簇 ID；
- 具体卖家问题；
- 适用条件；
- 总会话数；
- 人工介入类型和知识可复用性分布；
- 各解决方式变体及对应会话数；
- 原表行号；
- `live_agent_chat_session_id`；
- 客服答案是否一致；
- 需要知识负责人确认的内容。

如果同一会话包含多个独立问题，可分别进入不同问题簇，但必须保留相同来源行号和 session 以便回查。每个问题簇内部按唯一 `live_agent_chat_session_id` 去重计数；同一 session 在同一问题簇内只能计一次。

跨问题簇统计时必须区分两个口径：

- `问题簇命中次数`：各问题簇去重 session 数之和；同一多意图 session 可在不同问题簇中重复贡献，因此该数可以大于 RC 的唯一会话数。
- `RC唯一会话数`：所有问题簇 session ID 的并集去重数；用于报告该 RC 的总会话规模和整体占比，不能通过直接相加各问题簇会话数得到。

## 7. 高频和高价值问题排序

先让全部有效会话完成问题聚类和频次统计，再决定各问题簇优先建设哪一种 Chatbot 能力。

排序因素包括：

1. **会话频次**：相同具体问题出现越多，优先级越高。
2. **知识自助可行性**：无需后台查询或人工执行的问题适合优先知识化。
3. **API / Taskflow 可行性**：是否已有接口、所需输入和返回字段是否清晰。
4. **人工承接可优化性**：是否可以提前收集材料、说明触发条件并准确转接。
5. **业务影响**：是否影响发货、订单取消、罚分、资金或大批量订单。
6. **答案一致性**：存在冲突的问题应先由知识负责人确认。

若 SKB 覆盖率不是必要指标，可以只评估高频或高价值问题簇；其余标记为 `未评估`，不得视为 `未覆盖`。

## 8. 问题簇级 SKB 覆盖判断

SKB 覆盖判断只适用于问题簇中的 QA 解决方式变体。API / Taskflow（SOP）和人工承接 / 流程自动化计划不因缺少静态知识答案而被直接标记为 SKB `未覆盖`；待确认项作为依赖或未决状态记录。

### 8.1 检索方式

- 根据问题簇的具体卖家问题、适用条件和汇总客服方案定位候选 solution。
- 查看候选 solution 的完整 `message_content`，包括其中保留的 SEH 链接。
- 先按`solution_type_name`区分 QA 与 SOP。SOP 必须继续定位到具体`node_id + answer_branch_name`，逐个检查同一 node 下的所有相关 branch；不得只查看`node_name`，也不得将一个 branch 的答案套用到其他 branch。
- 将卖家问题簇的适用条件与 branch 的触发对象或 metrics 条件对应。若当前表只能看到`answer_branch_name`和答案、无法确认 branch 的实际 metrics 触发逻辑，应标记`待确认`并写明需 Owner 确认的路由条件，不得自行推断。
- 不需要无差别阅读全部 solution，也不需要为簇内每条会话重复检索。

### 8.2 比较对象

覆盖判断同时比较：

- 卖家的具体问题；
- 会改变答案的适用条件；
- 客服明确提供的通用方案；
- 候选 solution 对应 branch 的完整答案内容；
- SOP branch 的实际适用对象或 metrics 触发条件是否与问题簇条件一致。

### 8.3 覆盖结论

#### 完全覆盖

现有 solution 能回答问题簇中的卖家问题，并覆盖全部会改变处理路径的条件和客服通用方案。

依据格式：`solution「solution_name」（solution_id）覆盖了……`

完全覆盖的问题簇不进入知识 Optimization plan。

#### 部分覆盖

现有 solution 覆盖部分规则或路径，但缺少客服已经明确提供的关键条件、场景、步骤、链接或分支。

依据中先说明现有 solution 覆盖了什么，再说明缺少什么。

#### 未覆盖

没有适用于该具体问题和条件的 solution，或现有 solution 的站点、履约类型、订单状态或场景不适用。

#### 未评估

由于优先级、时间或信息不足，本轮没有进行 SKB 比较。`未评估`不得计入完全覆盖、部分覆盖或未覆盖。

若命中多个 solution，应分别说明每个 `solution「solution_name」（solution_id）` 覆盖的内容。若命中 SOP，覆盖依据必须精确写明`SOP ID + node_id + answer_branch_name`；同一 SOP 的不同 node 或 branch 分别说明，不得只写 SOP ID。

## 9. 可选的 SKB 覆盖程度分析

### 9.1 精确计算

如需得到知识可自助会话的精确覆盖分布，应评估全部知识问题簇，并将问题簇覆盖结论映射回簇内会话：

```text
某覆盖类型的唯一会话数 = 该覆盖类型下所有对应知识变体来源 session ID 的并集去重数
```

只有卖家问题、适用条件和知识解决方式均一致的会话，才能共享同一覆盖结论。一个一级问题簇存在多个解决方式变体时，覆盖结论只能映射到对应的知识变体来源会话，不能覆盖整个一级问题簇。

同一多意图会话可以在不同问题簇获得不同覆盖结论。按问题簇报告时，它在每个相关簇中各计一次；按 RC 报告唯一会话数或覆盖率时，必须回到 session 级去重，并单独说明含多个覆盖结论的重叠会话，不能把各簇会话数直接相加。

建议同时报告：

- 完全覆盖会话数和占比；
- 部分覆盖会话数和占比；
- 未覆盖会话数和占比；
- 未评估会话数和占比。

分母必须明确为：`可通过知识自助解决的会话数`。数据查询、处理执行和客服回复不完整的会话应单独报告，不直接作为知识库未覆盖。

### 9.2 快速估算

如果覆盖程度不是必要指标，可以只评估覆盖主要会话量的高频问题簇，并对剩余长尾问题保留 `未评估`。此时只能报告“已评估范围内的覆盖分布”或“覆盖下限”，不得表述为整个 RC 的精确覆盖率。

## 10. 从问题簇生成多路线 Optimization plan

一个卖家问题簇可以同时产生 QA、API / Taskflow（SOP）或人工承接 / 流程自动化 action。问题簇负责呈现完整需求频次；每条 action 负责说明具体建设内容。待确认事项写入依赖字段，不再单列第四种 action。

### QA 路线

当问题可以通过稳定、直接的规则、流程解释、步骤或链接回答，不需要读取卖家的具体订单、店铺、商品、物流、库存、配置或案件信息，也不需要变量、选择器、复杂条件判断或高阶自助流程时，使用 QA action。

### 部分覆盖

写明：

- 现有 QA solution 已覆盖的内容；
- 需要补充的适用条件或答案分支；
- 来源会话中客服明确提供的可复用内容。

缺口必须具体到可编辑内容，例如某站点规则、某订单状态下的处理、某操作入口或某条 SEH 链接，不能只写“答案不完整”。

### 未覆盖

只有当来源问题簇具有稳定问题、明确适用条件和可复用客服方案时，才建议新增 QA solution。不得把多个无关长尾问题放进同一 QA。

### QA 落点

- 可补充现有 QA：在 QA 优化计划中写明现有 `QA Solution ID + solution_name + node_id + answer_branch_name`及答案如何修改。
- 没有适用 QA：`QA Solution ID`标记`待新增`，并给出建议主题。
- 业务归属不明确：标记`待确认`，不得自行编造 QA Solution ID。
- 一个问题簇涉及多个 QA solution：每个 solution 单独一行；一个单元格只允许一个 QA Solution ID。
- 现有 QA 的修改落点必须精确到`QA Solution ID + node_id + answer_branch_name`；同一 QA 下若多个 branch 需要不同修改，应拆为不同 QA action。

### API / Taskflow 路线

当客服需要根据订单、物流、店铺、商品、库存、仓库配置、案件进度、卖家选择、变量或复杂条件判断返回对象级结果时，生成 API / Taskflow action，并落到 `solution_type_name = SOP` 的 solution。优先补充现有 SOP；没有合适 SOP 时新增 SOP。每条 action 至少记录：

- 触发该查询的卖家问题和适用条件；
- 现有或新增 SOP Solution ID；
- 卖家需要提供的入参；
- 客服实际执行的查询动作；
- 对话中实际返回的出参字段或状态；
- 查询成功后的最终卖家答案；答案中的动态值必须使用现有变量名，新增字段使用清晰的建议变量名并标注需 Function/Taskflow Owner 确认；
- 查询失败、无结果或接口不可用时的人工承接路径；
- SOP 对应的 `issue_id`、`issue_name`及本行落地后应增加的 issue-description 触发条件；
- 来源行号和 `live_agent_chat_session_id`。

不得把以下情况写成 API / Taskflow 需求：客服仅根据订单号确认订单属于 3PF、SLS、本土、跨境、Pick-up、Drop-off 等履约类型，并据此提供通用规则。此类履约类型应保留为问题簇和 solution 的适用条件。

不得根据客服未查询的内容自行增加输入字段、返回字段、系统能力或状态定义。

### 人工承接 / 流程自动化路线

当客服实际执行登记、建单、催促物流、升级案件、提交专员、补充材料或申请索赔时，可生成两类 action：

1. **Chatbot 人工承接优化**：在答案中说明何时需要联系人工、卖家需要准备哪些材料、应选择的咨询入口，以及客服明确说明的处理时效或后续通知方式。
2. **流程自动化候选**：仅当现有 Chatbot / Taskflow 具备或计划建设对应执行能力时，记录可自动完成的登记、建单、材料收集或状态跟进步骤。

材料清单、触发条件、时效和处理结果必须来源于客服明确回复。Chatbot 不得声称已经催促、建单或升级，除非系统实际完成该动作并返回结果。

### 待确认事项

客服回复不完整、适用条件缺失、答案冲突、业务归属不明确、接口字段缺失、SOP/issue 映射缺失、样本不足或低频长尾暂待累计的问题仍保留频次。`待确认`不再是行动类型：能够判断最终能力路线时，归入 QA、API/Taskflow 或人工承接，并把缺失项写入`待Owner确认/依赖`；无法安全判断行动路线时，保留在未决/长尾池，不编造 action。

### 行动类型与同一问题的多方案拆行

G列`行动类型`只使用以下3类：

- `QA`：稳定、直接的规则、流程解释、步骤或链接，不需要卖家对象级数据或复杂判断。
- `API/Taskflow`：需要卖家信息、变量、选择器、对象级后台查询、复杂条件或高阶自助流程；必须落到 SOP solution。
- `人工承接/流程自动化计划`：登记、建单、申诉、催促、升级、提交专员、补充材料或其他实际执行。

同一卖家问题涉及不同解决方案时，保留一个基础问题簇，并按可独立执行的行动拆成多行：

- 使用同一基础编号和行动后缀，例如`C01-Q1`、`C01-A1`、`C01-H1`；
- A–F和AA等问题簇共享字段在各行重复填写，H–J只填写支持本行行动的会话证据；
- 不同能力必须拆行；同一能力落到不同 QA solution 或不同 SOP solution 时也必须拆行；
- 同一 solution 下条件相容、可一次实施的分支可以合并，但必须在条件和方案中分别写清；
- 客服方案冲突时不得静默合并；保留在最匹配的行动行，并把冲突写入Z列`待Owner确认/依赖`；
- 如果其实是多个可分别回答、条件不同或能力不同的卖家意图，应分别进入不同问题簇，而不是作为同一问题的多方案。

完全覆盖且不需要采取任何行动的知识变体不写入 Optimization plan 行动明细，可记录在覆盖分析摘要中。

## 11. 优化建议与可直接复用答案

`QA优化计划与可直接复用的答案（仅忠实重组）`是给知识库维护者直接执行的字段，其中“可直接复用的答案”最终会由 Chatbot 面向卖家输出。答案必须改写为 **Chatbot 角色**，不能保留人工客服的内部处理口吻。

推荐结构：

```text
优化建议：在 QA solution「solution_name」（solution_id）中补充……；若无可复用的现有 QA，则新增 QA solution「建议名称」并配置以下答案。
可直接复用的答案：如您的……，请……；若……，请……。
```

O列只承载无需 API、变量、订单/店铺选择器或复杂条件判断即可回答的 QA 方案。涉及 API / Taskflow 的 SOP 建设统一写入 T–X：现有 SOP 必须同时包含真实的 SOP Solution ID、`node_id`和`answer_branch_name`，并直接描述该 branch 的 answer 如何修改；`node_name`只能辅助理解，不能代替`node_id`和`answer_branch_name`。若 branch 路由条件无法从来源表确认，不得猜测，应在 Z 列说明。

在忠实重组客服方案时，不只提取规则和步骤，也要关注客服如何让卖家更容易接受答案，例如先确认卖家所处场景、清楚解释原因和时效、说明下一步与查询入口、使用有依据的安抚或致歉表达。只有客服真实回复中已经出现、且脱敏后仍适合 Chatbot 复用的措辞才可保留；不得添加客服未表达的承诺、赔付结果、处理进度或情绪性保证。

### 11.1 Chatbot 角色要求

- 使用直接面向卖家的第二人称表达，例如`您`、`您的订单`、`请进入……`、`请准备……`。
- 答案应当脱离原会话也能单独成立：先说明适用条件，再给出卖家可执行的规则、步骤、链接或转人工指引。
- 不得使用人工客服的分析或内部口吻，例如：`客服查询确认……`、`我帮您查询了……`、`我已反馈后台……`、`我已催促……`、`我已创建工单……`、`转人工前收集……`。
- 如果静态 Chatbot 不能执行查询、建单、催促或升级，只能说明下一步，例如：`请准备订单号和异常截图后联系在线客服进一步核实`；不得写成已经完成该动作。
- 只有当实际 Taskflow 已在当前对话中成功执行并返回结果时，Chatbot 才能使用`已为您查询到……`、`已提交……`或`跟进编号为……`等完成式表述。
- 如果答案依赖 API 查询结果，应使用条件分支，例如：`若查询结果显示订单仍在分配尾程物流，请……`。未建设或未调用 API 时，不得假装已获得查询结果。
- `优化建议`是给知识库维护者看的内部行动说明；`可直接复用的答案`是给卖家看的 Chatbot 输出，两者不得混写。

#### 11.1.1 内部证据语言与卖家答案强制隔离

L、M、N、T、Y、Z 等内部字段可以使用证据或分析口吻；O 列中`可直接复用的答案：`之后，以及 T 列 SOP 计划中的`最终输出答案：`之后，只能出现 Chatbot 面向卖家的答案。以下来源归因或内部工作措辞不得出现在卖家答案部分：

- `客服回复`、`客服说明`、`客服表示`、`客服确认`；
- `客服查询`、`客服未查询到`、`客服提供`、`客服建议`；
- `根据客服`、`人工客服`、`转接后`、`专员回复`。

不得通过简单删除`客服回复`来制造确定性规则。改写时必须同时满足：

1. 保留来源对话明确支持的适用条件；
2. 保留来源结论的确定性强度，不把`未查到/未确认`强化为`平台没有/不支持`；
3. 不把客服个案查询或处理结果泛化为通用知识；
4. 改写后的句子能够由 Chatbot 直接对卖家说出。

示例：

```text
不合格：泰国站点客服回复为3PF佣金不区分类目。
合格：如您咨询泰国3PF佣金，佣金不按商品类目区分。
```

```text
不合格：客服当前未查询到该站点的3PF尾程价卡。
仅当客服明确说明平台没有该价卡时才可改写：该站点目前没有平台提供的3PF尾程价卡，请联系对应物流商确认。
若客服只是本次未查到，O列不得形成上述答案，应在M列记录查询情况并在Z列标记待Owner确认。
```

若来源只提供`通常`、`一般情况下`等模糊结论，且没有明确条件可替换，不得删除限定词并改写成绝对规则。此时将缺失条件写入 Z 列，O 列不形成可直接复用答案。

### 11.2 Google Sheets 单元格格式

- 同一单元格内先写`优化建议：`，换行后写`可直接复用的答案：`。
- `优化建议`和`可直接复用的答案`两个标签使用富文本加粗；冒号后的正文不加粗。
- 不使用 Markdown 星号代替 Google Sheets 富文本加粗。
- 对于`API/Taskflow`和`人工承接/流程自动化计划`行动，O列留空；对应计划分别写入 T–X 或 Y。待确认事项写入 Z，不创建单独行动行。

强制要求：

- 每一个方案必须明确适用条件。
- 禁止用“一般情况下”“通常”“原则上”“大多数情况下”“视情况而定”等笼统措辞代替条件。
- 汇总答案的每项内容必须能追溯到来源问题簇中的客服回复。
- 只有适用条件相容时，才能组合多条会话中客服提供的内容。
- 客服答案存在冲突时，不得静默合并，应标记知识负责人确认。
- 删除订单号、运单号、店铺 ID、商品 ID、姓名、电话、邮箱、详细地址和聊天编号等个案信息。
- 不得把个案查询结果无条件泛化为通用规则。
- 客服未说明必要条件时，在 M/Z 列写明`客服未说明该方案的适用条件，需知识负责人确认`，O 列留空，不得把这句内部说明写入卖家答案。
- 客服仅返回个案查询结果时，在 M 列写明`客服仅返回个案查询结果，未提供可通用复用的静态答案`；若适合对象级查询，则转为 API/Taskflow 计划并在 T 列说明，O 列留空。

### 11.3 O/T卖家答案写入前与回读后的强制角色校验

对每个非空 O 单元格`可直接复用的答案：`之后的文本，以及每个非空 T 单元格`最终输出答案：`之后的文本执行以下检查；任一项失败时禁止写入，已经写入时停止后续批次并只修正当前输出：

1. 单元格必须且只能按`优化建议：……\n可直接复用的答案：……`分为两个角色区段。
2. 只对`可直接复用的答案：`之后的文本执行卖家答案检查；`优化建议`中的内部维护措辞不因此误报。
3. 答案部分不得包含本节 11.1.1 的来源归因/内部工作措辞。
4. 答案部分不得声称已查询、已提交、已反馈、已催促、已升级或已建单，除非当前 Taskflow 已真实执行并返回成功结果。
5. 答案部分不得使用`一般情况下`、`通常`、`原则上`、`大多数情况下`、`视情况而定`替代适用条件。
6. 每项规则必须能追溯到行动证据会话中的客服明确回复，且确定性强度没有被提高。
7. 写入后回读同一 O/T 范围并再次执行上述检查；Connector/API 的成功响应不能代替角色校验。

## 12. Issue description 同步维护

QA 或 SOP solution 增加新的解决场景后，只有实际执行该行 QA/SOP 修改时，才同步扩大对应 issue description 的匹配范围。

每个 QA 计划行维护 P–S：QA Solution ID、QA `issue_id`、QA `issue_name`、`若本QA行动落地，建议同步修改 issue description`。

每个 API/Taskflow（SOP）计划行维护 U–X：SOP Solution ID、SOP `issue_id`、SOP `issue_name`、`若本SOP行动落地，建议同步修改 issue description`。

规则：

- 现有 QA/SOP：只写本行落地后需要新增的核心定义或触发条件，不提前合并其他尚未执行的计划。
- 新增 QA/SOP：Solution ID 写`待新增`，`issue_id`写`待创建`，`issue_name`写建议名称，并在本行给出新 issue 的完整初始 description。
- 映射或业务归属不明确：保留`待确认`，在 Z 列说明缺失项，不编造 issue ID。
- 现有 Tool 类型 SOP 在 issue-and-solution 来源中没有绑定 issue 时：U 写真实 SOP Solution ID；V 写`待确认`；W 明确写`Tool SOP暂无绑定issue，待Owner确认`；X 只写`若后续映射到对应issue，建议新增触发条件：……`，不得猜测 issue ID。
- 同一 QA 或 SOP 有多行修改计划时，每行保持独立；最终只合并实际被执行的修改。
- 一行只对应一个 QA solution 或一个 SOP solution；涉及多个 solution 时必须拆行。
- issue description 只描述“什么卖家意图应该匹配该 issue”，不把不必要的答案步骤写成触发条件。

新 issue 的完整 description 使用以下结构：

```text
1️⃣ 核心定义（Core Definition）
当卖家……时，适用此问题类型。
2️⃣ 适用范围 / 触发条件（Applicability / Conditions）
在以下情况下，应触发该问题类型：
• 卖家……；
• 卖家……。
```

## 13. 优先级

综合考虑：

1. 问题簇会话频次；
2. QA 自助或 API/SOP 自助可行性；
3. 覆盖缺口严重程度；
4. 客服答案成熟度和一致性；
5. QA/SOP 落点与 issue 归属清晰度；
6. 业务影响。

建议口径：

- P0：高频、客服方案清晰，且可快速补充现有 QA，或现有 SOP/API 已具备能力、只需小幅配置即可自助解决。
- P1：高频人工承接问题可通过明确材料清单、转接路径或已有 API / Taskflow 改善；或 QA 答案需要按站点、状态、渠道拆分后复用。
- P2：需要新增 SOP/API/Taskflow 或处理自动化能力；或问题低频、长尾、跨业务线、归属不清、答案冲突、客服信息不足。

API / Taskflow action 可默认列为 P2 能力建设；若问题高频、业务影响大且现有接口已经具备，可提升为 P1。

| N | `建议行动` | 所有 action | 用内部行动口吻写清`做什么 + 由哪个能力/solution承担 + 关键限制`。 |
| O | `QA优化计划与可直接复用的答案（仅忠实重组）` | 仅 QA 必填 | 固定为`优化建议：……\n可直接复用的答案：……`；两个标签富文本加粗。说明补充现有 QA solution 或新增 QA；答案以 Chatbot 角色直接面向卖家，并通过11.3校验。 |
| P | `QA Solution ID` | 仅 QA 必填 | 现有 QA 写真实 solution ID；新增写`待新增`；归属不清写`待确认`。一行只能写一个 QA Solution ID。 |
| Q | `QA issue_id` | 仅 QA 必填 | 现有映射写真实 ID；新增写`待创建`；无法映射写`待确认`。以纯文本保存。 |
| R | `QA issue_name` | 仅 QA 必填 | 现有写真实 issue name；新增写建议名称；无法映射写`待确认`并在 Z 说明。 |
| S | `若本QA行动落地，建议同步修改issue description` | 仅 QA 必填 | 现有 issue 只写本行落地后的增量触发条件；新增 issue 写完整两段式 description。 |
| T | `SOP优化计划（API/Taskflow）` | 仅 API/Taskflow 必填 | 先说明补充现有 SOP 或新增 SOP；固定包含`触发条件`、`入参`、`查询/执行`、`出参`、`最终输出答案`、`失败/无结果`。现有 SOP 写清`SOP Solution ID + node_id + answer_branch_name + answer 如何修改`。动态值使用现有变量名；拟新增字段写明确的建议变量名并在 Z 标记依赖。只写来源支持的能力；仅确认履约类型不得形成 API。 |
| U | `SOP Solution ID` | 仅 API/Taskflow 必填 | 现有 SOP 写真实 ID；新增写`待新增`；归属不清写`待确认`。一行只能写一个 SOP Solution ID。 |
| V | `SOP issue_id` | 仅 API/Taskflow 必填 | 现有映射写真实 ID；新增写`待创建`；Tool SOP 无绑定 issue 或无法映射时写`待确认`，不得猜测。 |
| W | `SOP issue_name` | 仅 API/Taskflow 必填 | 现有写真实 issue name；新增写建议名称；Tool SOP 无绑定 issue 时写`Tool SOP暂无绑定issue，待Owner确认`。 |
| X | `若本SOP行动落地，建议同步修改issue description` | 仅 API/Taskflow 必填 | 现有 issue 写本行增量触发条件；新增 issue 写完整两段式 description；Tool SOP 未绑定 issue 时写条件式建议：`若后续映射到对应issue，建议新增触发条件：……`。 |
| Y | `人工承接/流程自动化计划` | 仅人工 action 必填 | 固定顺序：`触发条件：……；卖家需准备：……；承接动作：……；通知方式/时效：……；可自动化：……`。只写客服明确要求和实际处理；未说明写`客服未说明`。 |
| Z | `待Owner确认/依赖` | 按需填写 | 写具体口径、冲突、阈值、接口字段、变量、能力 Owner、QA/SOP/issue 映射或前置依赖。格式优先为`待确认：……；依赖：……`。 |
| AA | `知识可复用性分布（仅描述，不作筛选）` | 所有 action | 固定顺序：`可形成通用答案n；仅个案查询结果n；仅人工处理n；客服回复不完整n`；同簇多行重复同一分布。 |
| AB | `备注` | 按需填写 | 记录多意图证据、统计口径、履约类型查询例外、长尾池或其他审阅事项。 |
| AC | `PIC` | 人工维护 | 默认留空，除非用户已明确指定。 |
| AD | `Feedback` | 人工维护 | 默认留空，供 reviewer 记录采纳、驳回、修改或执行结果。 |

### 14.3 表头分区与颜色

- A:N：公共信息与分析依据，使用深橙红底。
- O:S：`QA 优化计划`分区，使用金黄色底。
- T:X：`SOP 优化计划（API/Taskflow）`分区，使用蓝色底。
- Y：`人工承接/流程自动化计划`分区，使用绿色底。
- Z:AD：依赖、统计与审阅分区，使用灰色底。
- 所有表头统一白色加粗、水平和垂直居中、自动换行；数据区可使用对应分区的浅色底，但不得降低可读性。

### 14.4 行类型与字段填写矩阵

| action 类型 | K–N | O–S QA | T–X SOP/API | Y 人工 | Z | AA–AB |
| --- | --- | --- | --- | --- | --- | --- |
| `QA` | 必填 | 必填；现有 QA 写真实 P/Q/R，新增 P=`待新增`、Q=`待创建` | 全部留空 | 留空 | 按需 | AA必填，AB按需 |
| `API/Taskflow` | 必填 | 全部留空 | 必填；现有 SOP 写真实 U/V/W，新增 U=`待新增`、V=`待创建` | 留空 | 必填 Owner、接口、变量和映射依赖；无额外依赖时写`无` | AA必填，AB按需 |
| `人工承接/流程自动化计划` | 必填 | 全部留空 | 全部留空 | 必填 | 按需 | AA必填，AB按需 |

### 14.5 一行一 action 与一行一 solution

- 同一问题簇可以产生多条 action，但每行只描述 QA、API/Taskflow 或人工承接中的一种能力建设。
- 同一问题同时需要 QA 解释和 API 查询时，拆成 `Q`、`A` 两行，分别填写 O–S 和 T–X；不得把两套计划堆在一行。
- 同一行动涉及两个 QA solution 或两个 SOP solution 时必须拆行；每行只对应一个 solution/issue。
- 同一 SOP 的不同`node_id`或`answer_branch_name`需要不同修改时也应拆行；仅当条件相容、可一次实施且目标 branch 相同，才可合并。
- 相同基础 Cluster ID 的共享字段重复填写；分别使用`Q/A/H`后缀，并只填写本行行动的证据。
- 客服方案冲突时不得静默合并；在最匹配的行动行 Z 列写明冲突和待确认项。无法安全判断行动路线的内容留在未决/长尾池，不编造行动行。
- 数据行不得纵向合并。即使 A–F、AA 在同簇多行重复，也应完整填写，以便按 solution ID 筛选审阅。
- E 是问题簇去重会话数，H 是本行 action 证据会话数，二者不得互换。

### 14.6 O列 Chatbot 答案验收示例

合格：

```text
优化建议：在现有 QA solution「为什么3PF订单无法发货/无法打印面单」（SOP2092）中补充基础排查无效后的诊断升级步骤。
可直接复用的答案：如检查网络、更换浏览器、清除浏览器缓存及使用谷歌浏览器无痕模式后仍无法发货或获取面单，请使用诊断工具录制完整操作并生成UID。同时请准备店铺账号、订单号和联系邮箱，以便联系在线客服进一步排查。
```

不合格：

```text
客服查询后确认您的订单有异常，我已帮您提交技术团队并加急，请等待邮件。
```

不合格原因：保留了人工客服角色，声称已查询、提交和加急；静态 Chatbot 并未执行这些动作，也没有先写清适用条件。

另一类不合格：

```text
可直接复用的答案：越南站点客服回复……；泰国站点客服回复为……。
```

不合格原因：答案仍在向卖家描述证据来源，而不是直接回答卖家。相关来源说明应放在 M 列；O 列只保留条件化后的卖家答案。

## 15. 验收清单

- 全部会话先完成问题、条件、客服方案、人工介入和知识可复用性标注，没有逐会话重复比较 SKB。
- 全部有效会话均进入一级卖家问题聚类；知识可复用性和人工介入类型未被用作聚类前筛选条件。
- 多意图会话在逐会话阶段保留为一个来源行并编号标注，没有只选主意图；Optimization plan 阶段各独立意图已分别进入相应问题簇。
- 仅同一问题的补充描述或追问未被误拆；多意图会话中未答复的意图已明确标记，未自行补全。
- 问题簇落到具体卖家问题，不停留在宽泛主题。
- 一级问题簇按卖家问题和适用条件合并；不同客服方案、查询和处理动作在簇内保留为二级解决方式变体。
- 每个问题簇保留会话数、原表行号和 session ID，可追溯到完整 `msg_data`。
- 问题簇内部按 session 去重；跨簇汇总明确区分`问题簇命中次数`和`RC唯一会话数`，未直接相加多意图重叠会话。
- 多意图会话的会话级人工介入按最高实际动作标注；每条 action 的证据仍注明并只使用对应意图的客服方案、查询或执行内容。
- 仅确认订单履约类型未被标记为人工数据查询，也未生成 API / Taskflow 需求；履约类型已保留为适用条件。
- SKB 覆盖判断在问题簇的知识解决方式变体层级完成，并读取完整 `message_content`；SOP 已按`Solution ID + node_id + answer_branch_name`逐 branch 判断，没有合并不同 metrics branch。
- `未评估`与`未覆盖`严格区分。
- 覆盖率明确分母；数据查询和处理执行不被直接算作知识库未覆盖。
- QA 路线只有部分覆盖或未覆盖且需要修改的变体进入 QA action；API 与人工承接路线独立生成相应 action；待确认只作为依赖或未决池状态。
- G列只出现`QA`、`API/Taskflow`、`人工承接/流程自动化计划`三类值。
- 一个 action 一行、一个 solution 一行；QA 和 SOP 的 Solution ID、issue ID 可分别筛选。
- 现有 SOP 的每条 API/Taskflow 建议已写明`SOP Solution ID + node_id + answer_branch_name + 该 branch 的 answer 如何修改`；不同修改目标已拆行。
- 每条 API / Taskflow action 写清入参、查询/执行、出参、最终输出答案和失败/无结果路线；变量名和待新增字段已显式标注，未添加客服对话未支持的系统能力。
- 每条人工承接 action 写清触发条件和客服明确要求的材料；未把未执行的动作表述为已完成。
- 每条 QA/SOP 建议明确适用条件，可复用内容有来源，个案信息已脱敏。
- QA 行已维护 P–S；API/Taskflow（SOP）行已维护 U–X。Tool SOP 未绑定 issue 时未猜测 issue ID，使用条件式 issue-description 建议。
- O列答案已与内部证据语言隔离；`可直接复用的答案：`之后不存在`客服回复/说明/查询/提供/建议`、`根据客服`、`转接后`或`专员回复`等措辞。
- T列`最终输出答案：`之后同样通过 Chatbot 角色校验；动态值使用变量名，未假装已经查询或执行。
- 若来源仅支持`未查到/未确认`或模糊口径，没有把它强化为`平台没有/不支持`或其他确定规则；条件不足的内容已转入Z列待确认，O列保持空白。
- Issue description 仅在对应 QA/SOP 修改实际落地时同步，不提前合并未执行计划。
- 实施后使用来源问题进行意图匹配和答案回归测试。
